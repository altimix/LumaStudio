# ハードウェア書き出しと不要な合成の省略

Issue: #3

- Mac Apple SiliconはVideoToolbox、WindowsはNVENC・Quick Sync・AMFを候補にする。実際のH.264エンコードに成功した方式だけ選択可能にする。
- VideoToolboxはソフトウェア代替を禁止して検出し、自動選択で利用可能ならCPUより優先する。Apple Siliconの品質指定はドラフト50・標準65・高画質75。CPUのCRF値とは同一尺度ではない。
- WindowsのFFmpegは固定したMITライセンスのnv-codec-headers・AMFヘッダー・oneVPLディスパッチャーを使う。対応ソースとライセンスを提供し、nonfree構成は使わない。各ベンダーのドライバーは利用者のPCに必要。
- 自動選択したハードウェアの初期化・処理に失敗した場合だけCPUで再試行する。素材不正・ディスク不足・中止では再試行しない。既存ファイルは完成後にのみ置換する。
- 無補正のクリップでは恒等色変換を省く。単一の不透明な映像が出力全期間・全画面を占め、変形・フェード・トランジションがない場合はRGBA変換と背景合成を省く。テロップ、重ね合わせ、隙間、アスペクト比違い等は従来の合成を使う。
- 圧縮だけでなく実プロジェクトの書き出し時間を比較する。速度は素材・編集内容・PCによって異なり、固定倍率は保証しない。`node scripts/benchmark-export.cjs`でデモ映像の1080p/4Kを比較できる。
- 検証はフレーム・音声・長さ・中止・CPU再試行を含める。Windows CIでは3方式の組み込みとGPU非搭載時の動作を確認する。Windows各ベンダーの実機性能は未確認として明記する。

1.0.0の公開済み配布物は変更しない。GPU対応Windowsメディアツールはこのソースから`npm run build:media`で構築する。既存の`prepare:media`が取得するmedia-tools-v1はCPU構成である。

Windowsの新規MSYS2環境でも同じ手順で構築できるよう、依存ライブラリの構成判定に必要なdiffutilsを明示的に導入する。CMake・MinGW makeを含む導入コマンドは`docs/DEVELOPMENT.md`とWindows CIで一致させる。

固定oneVPLの`mfx_dispatcher_defs.h`は、未定義の`_MSC_VER`を0として扱いMinGWにも古いMSVC向けの`wcscpy_s`・`wcscat_s`マクロを適用する。新しいMinGWヘッダーとの衝突を避けるため、Windowsビルド時に条件を`defined(_MSC_VER) && _MSC_VER < 1400`へ限定する。元アーカイブのSHA256検証は維持し、展開後の変更は配布する`build-media.sh`で再現する。想定する条件が1箇所でない場合はビルドを中断する。

## 実測例

Apple M2 Pro、付属デモ映像8秒、単一無加工クリップ、30fps・標準品質。ほかのテストを止めて各1回計測。

| 出力 | 最適化後CPU | VideoToolbox |
| --- | ---: | ---: |
| 1920×1080 | 3.91秒 | 1.32秒 |
| 3840×2160 | 15.96秒 | 4.47秒 |

各方式の標準品質設定であり、ビットレートや圧縮品質の尺度は同一ではない。GPU出力のフレーム・音声・長さは別の回帰テストでも比較する。

## レビュー後の補足

高速な合成省略はアルファを持たないH.264素材に限定する。ProResなど透明度を含み得る映像は従来の合成を維持する。回転メタデータによりデコード後の縦横が変わっても、中央パディングで出力寸法を保つ。90度・270度の実動画で検証する。

Mac CIのハードウェアH.264で黒画素の最大値3/255、平均0.00625/255を実ファイルから確認した。黒背景テストは最大4/255かつ平均0.1/255未満を要求し、圧縮の丸めと実際の黒浮きを区別する。
