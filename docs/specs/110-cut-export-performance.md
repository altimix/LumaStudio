# カットだけの映像の書き出し高速化（Issue #110）

## 目的

不透明な H.264 映像を画面いっぱいに並べたカット編集では、全クリップを RGBA に変換して黒背景へ重ねる処理を省く。音声の入力、先読み、音量処理、AAC エンコードは従来どおりとする。

## 適用条件

- 表示される映像が同じトラックにあり、先頭から最後まで隙間も重なりもない。
- 素材は H.264 で、記録された縦横比が書き出しの縦横比と一致する。
- 拡大縮小、移動、回転、透過、フェード、色補正、モザイク、ぼかし、マスク、クロマキー、視覚キーフレーム、トランジションがない。
- 複数クリップの場合、切り口は書き出しフレームと素材フレームの境界に一致する。

同じ素材を連続した参照区間に分割している場合、映像だけを一つの参照区間に結合して一回デコードする。素材の切り替えを含む場合は、素材 FPS と書き出し FPS が一致し、各クリップが二フレーム以上なら FFmpeg の `concat` フィルターで接続する。一フレームの区間は `concat` で長さが失われるため、従来の合成処理を使う。いずれの条件にも合わない編集も従来どおり扱う。

## 時間と音声

区間の終了は含めず、映像の切り口を出力フレーム境界で判定する。結合するのは映像のみ。音声は元のクリップ単位で読み、AAC の先読みとミックスを維持する。元素材を変更せず、出力は従来どおり一時ファイル完成後に置き換える。

## 測定と受け入れ

`node scripts/benchmark-export-cuts.cjs test-results/export-cuts` は同梱デモの二秒、960×540、CPU 標準品質を測る。24 FPS、24 カットの手元測定では、連続分割が 0.645 秒から 0.181 秒、交互に離れた素材位置へ切り替えるカットが 0.627 秒から 0.445 秒になった。30 FPS のカットは出力フレームと切り口が一致しないため従来経路となり、速度はほぼ変わらない。測定値は端末、素材、エンコーダーで変わる。

自動検証では、連続分割の映像入力が一つで音声入力が各クリップに残ること、異なる素材の境界と音声が残ること、1 フレームおよび 2 フレームの交互カットで全フレームが正しい順序にあること、効果・隙間・出力フレームに揃わない切り口が従来経路になることを確認する。Windows ではパッケージ版の書き出しと再読込も確認する。
