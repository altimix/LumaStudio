# Windows の一時的な保存先ロック

Issue #77。Windows CIでモニターのUndo後の保存が停止した原因は、保存先へのatomic renameがEPERMで拒否されたことだった。診断用のキー入力とトースト記録で確認した。メーターの受け入れ検証を通す際の保存の信頼性修正として同じPRに含める。

Windows上のEPERM / EACCES / EBUSYだけを、25〜400msの待機を挟んで最大8回再試行する（待機合計1975ms）。書き込み完了した同じ一時ファイルを使用し、成功まで元の保存ファイルをそのまま残す。古いファイルの事前削除は行わない。その他のエラーは即座に返し、永続的な拒否も回数上限で失敗として返す。一時ファイルは成功・失敗時に片付ける。

同じ保存先への書き込みは順番に処理し、古い保存の再試行が新しい保存を上書きしないようにする。ある保存が失敗しても、後続の保存は試行できる。別の保存先は並行して処理できる。保存先のキーは絶対パス（Windowsでは小文字）で管理する。

テストは実ファイルへの書き込みに一時的な置換拒否を注入し、元ファイル保持、同じ完成済み一時ファイルの再利用、永続エラーの上限と片付け、別種エラー、後続の回復、連続保存の順序を確認する。パッケージ化したWindowsアプリでも保存ボタンから実際のIPCを通し、2回のEPERMから3回目で成功することと元ファイルの保持を確認する。Windowsの既存保存・モニター・終了・復元検証も維持する。
